# DEC-010：MVP 采用任务质量、可靠性与用户效率三维评价框架

## Type

Product

## Status

Accepted

## Decision

AI Ecommerce Agent 的 MVP 使用以下三类指标评价产品效果：

1. 任务质量；
2. 结果可靠性；
3. 用户效率。

产品**不得**仅以模型输出是否流畅、内容是否看起来专业或最终商品销量是否提升，作为 MVP 是否成功的唯一判断依据。

## Evaluation Dimension 1：任务质量

任务质量用于判断系统生成的商品定位分析和营销 Brief 是否完整、合理并可供运营人员使用。

可评估内容包括：

- 商品事实覆盖情况；
- 关键卖点覆盖情况；
- 四层营销 Brief 完整情况；
- 商品定位与输入资料的一致性；
- 营销 Brief 对实际运营工作的可用性；
- 用户是否需要对输出进行大规模修改；
- 关键结论是否被运营人员接受。

> 具体计算公式和目标值后续确定。

## Evaluation Dimension 2：结果可靠性

可靠性用于判断系统是否正确区分事实、洞察、推断、假设和资料不足，并保留重要结论的依据关系。

可评估内容包括：

- 明确事实的来源可追溯率；
- 事实与推断的分类准确性；
- 无依据事实数量；
- 伪造引用或伪造来源数量；
- 资料冲突识别情况；
- 资料不足标记情况；
- 上游内容修改后，下游阶段是否被正确标记为失效；
- 局部重跑后各层内容是否保持一致。

> 具体自动评测和人工评测方式后续确定。

## Evaluation Dimension 3：用户效率

用户效率用于判断产品是否降低商品运营和内容运营人员完成商品上新分析与营销 Brief 的成本。

可评估内容包括：

- 从提交资料到获得可用 Brief 的总耗时；
- 与纯人工流程相比节省的时间；
- 用户补充资料的轮次；
- 审核节点中的修改数量；
- 完成一份可用 Brief 的成功率；
- 人工修改工作量；
- 用户完成任务所需的交互步骤。

> 具体对照实验方式和样本规模后续确定。

## MVP Priority Metrics

MVP 优先关注以下六项核心指标：

### Metric 1：事实来源可追溯率

衡量被标记为「明确事实」的内容中，有多少能够关联到真实用户输入或资料来源。

### Metric 2：无依据事实数量

衡量输出中出现了多少无法从输入资料、用户确认或已读取来源中得到支持，却被错误表达为事实的内容。

> 目标方向应是尽可能接近零，但具体验收阈值尚未确定。

### Metric 3：四层 Brief 完整率

衡量事实层、洞察层、策略层和执行层中，要求输出的必要部分是否完整生成。

> 具体必填字段需要在后续数据契约讨论中确定。

### Metric 4：关键结论人工接受率

衡量用户在审核节点中，对目标用户、用户需求、购买阻碍、商品定位、卖点优先级等关键结论直接接受或仅轻微修改的比例。

> 具体「接受」和「轻微修改」的定义后续确定。

### Metric 5：生成可用 Brief 的任务完成时间

衡量用户从开始提交资料，到获得经过审核、可用于后续内容工作的营销 Brief 所需时间。

评估时应包含：

- 资料填写；
- 系统分析；
- 用户审核；
- 局部重跑；
- 最终 Brief 生成。

### Metric 6：下游失效正确率

衡量用户修改事实层、洞察层或策略层的重要内容后，系统是否正确识别并标记需要重新生成的下游阶段。

## Evaluation Principle

评价逻辑为：

```
任务是否完成
+
结果是否可信
+
用户是否节省时间和工作量
```

不能只评价：

```
输出是否流畅
或
页面是否看起来专业
```

也不能在缺少真实、长期商业数据的作品集阶段，直接把：

```
销量提升
```

作为唯一核心指标。

> 销量、点击率、转化率和互动率可以作为未来真实试点中的业务结果指标，但当前**不是** MVP 唯一验收依据。

## Reason

只评价输出质量，容易将产品变成「内容写得像样」的模型 Demo，无法证明真实工作价值。

只评价效率，又可能出现结果生成很快，但事实错误、依据不足或不可使用的情况。

直接评价最终销量存在以下限制：

- 作品集阶段通常没有长期真实经营数据；
- 销量受到价格、品牌、渠道、预算、库存和季节等多种因素影响；
- 无法将变化完全归因于 Agent；
- 测试周期过长；
- 不适合作为首个 MVP 的唯一成功标准。

三维评价框架能够同时覆盖：

- 产品交付物是否可用；
- 输出是否可信；
- 是否真正减少运营人员工作成本。

## Impact

该决定将影响：

- PRD；
- MVP Scope；
- 验收标准；
- 测试设计；
- 数据采集；
- 事件埋点；
- 用户研究；
- Demo 对比实验；
- RAG 和引用机制；
- 人工审核流程；
- 工作流状态与局部重跑测试；
- README；
- 项目复盘；
- 简历项目成果表达。

> 后续技术方案和开源仓库筛选需要考虑：是否能够记录任务过程、中间结果、来源关系、用户修改和各阶段耗时，以支持这些评价指标？

## Decision Boundary

**本决定已经确认：**

- MVP 使用任务质量、可靠性和用户效率三类指标；
- 不把语言流畅度作为唯一标准；
- 不把最终销量作为 MVP 唯一标准；
- 优先关注六项核心指标；
- 自动评价与人工评价可能同时存在。

**本决定尚未确认：**

- 每项指标的具体公式；
- 每项指标的目标阈值；
- 测试数据集；
- 用户测试人数；
- 人工评分标准；
- 是否使用 LLM-as-a-Judge；
- 埋点方案；
- 对照组设计；
- 测试环境；
- 是否在 MVP 中接入真实业务数据；
- 是否展示评测 Dashboard。
