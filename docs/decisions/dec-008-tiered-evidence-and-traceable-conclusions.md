# DEC-008：MVP 采用分级证据标记与结论可追溯机制

## Type

Product

## Status

Accepted — Amended by DEC-047

> **Current amendment:** [DEC-047](dec-047-progressive-evidence-edit-intent-and-actionable-recovery-interactions.md) 冻结五类标记的渐进式证据展示、真实可用定位和非数字置信度边界；本决定以下原文保留为 2026-07-27 的可靠性原则记录。

## Decision

AI Ecommerce Agent 的 MVP 必须明确区分不同类型的信息和结论，**不得**将用户输入、资料事实、模型分析和未经验证的假设混合呈现。

MVP 采用以下**五类**证据与结论标记：

1. 明确事实；
2. 有证据洞察；
3. 模型推断；
4. 待验证假设；
5. 资料不足。

重要结论需要保留与主要依据、输入资料或前序分析结果之间的关系。

## Evidence and Conclusion Types

### 1. 明确事实

- **定义：** 能够直接从用户输入或已提供资料中确认的信息。
- **示例：**
  - 商品重量为 320g；
  - 商品售价为 299 元；
  - 商品材质为铝合金；
  - 用户明确将「便携」列为主要卖点。
- **要求：**
  - 必须能够追溯到用户输入或具体资料来源；
  - 不得由模型自行补充；
  - 来源不存在时不得标记为明确事实。

### 2. 有证据洞察

- **定义：** 由一个或多个事实、评论、调研资料或其他输入支持的分析结论。
- **示例：**
  - 用户可能重视便携性；
  - 评论中频繁出现对续航能力的关注；
  - 部分用户将价格视为购买阻碍。
- **要求：**
  - 应说明主要依据；
  - 不要求每项洞察都对应一条完全相同的原文；
  - 但必须存在能够支持该洞察的资料或事实。

### 3. 模型推断

- **定义：** 模型基于多个事实和洞察进行综合分析后形成的判断。
- **示例：**
  - 可以将商品定位为轻量通勤产品；
  - 核心传播方向可以强调差旅和日常携带；
  - 卖点优先级可以先突出便携，再突出耐用。
- **要求：**
  - 必须明确标记为推断；
  - 应说明使用了哪些主要事实或洞察；
  - 不得伪装成用户已经提供的事实。

### 4. 待验证假设

- **定义：** 对营销策略可能有价值，但当前资料不足以确认的判断。
- **示例：**
  - 目标用户可能愿意为环保材质支付溢价；
  - 年轻女性可能是最具潜力的消费群体；
  - 某种内容角度可能提高种草效果。
- **要求：**
  - 必须提示需要用户确认或后续验证；
  - 不得直接作为最终营销事实使用；
  - 用户可以接受、否定或保留该假设。

### 5. 资料不足

- **定义：** 当前信息不足以形成可靠判断的事项。
- **示例：**
  - 无法判断目标用户的价格敏感度；
  - 无法验证商品是否优于竞品；
  - 无法确认某项功能是否适合特定人群。
- **要求：**
  - 必须明确表达无法判断；
  - 不得通过模型常识自动补全；
  - 可以建议用户补充资料。

## Minimum Reliability Principles

MVP 至少遵守以下原则：

### Principle 1：事实可追溯

所有明确事实必须能够追溯到：

- 用户填写的字段；
- 用户上传的资料；
- 已确认的外部信息来源；
- 用户在审核阶段作出的修正。

### Principle 2：事实与推断分离

系统必须在内部数据和用户可见输出中区分：

- 事实；
- 洞察；
- 推断；
- 假设；
- 无法判断事项。

### Principle 3：重要洞察保留依据

影响目标用户、商品定位、卖点优先级和内容策略的重要洞察，应保留主要依据。

### Principle 4：资料不足时保持诚实

当资料不足时，系统应：

- 标记资料不足；
- 降低结论确定性；
- 提出补充资料建议；
- 或将相关内容标记为待验证假设。

**不得**自动编造缺失事实。

### Principle 5：策略可以回溯

重要策略结论应能够回溯到：

- 明确事实；
- 有证据洞察；
- 用户确认的假设；
- 用户在审核节点作出的修改。

### Principle 6：修改产生依赖影响

当用户在审核节点修改某项事实或关键洞察时，依赖该内容的后续策略和执行 Brief **不应**继续被视为有效。

系统后续需要支持：

- 重新生成；
- 标记失效；
- 或提示用户相关内容需要更新。

> 具体重跑机制尚未确定。

### Principle 7：禁止伪造来源

系统**不得**：

- 生成不存在的文档名称；
- 伪造评论原文；
- 伪造引用编号；
- 将模型常识包装为用户资料；
- 引用未被系统实际读取的来源。

## Internal Relationship

输出内部至少需要表达类似关系：

```
输入资料或用户事实
        ↓
明确事实
        ↓
有证据洞察
        ↓
模型推断或待验证假设
        ↓
商品定位与营销策略
        ↓
执行层营销 Brief
```

后续层级的重要结论应能够关联其主要上游依据。

> 该关系**不代表**前端必须显示复杂的知识图谱或完整推理链。前端具体如何展示（来源标签 / 引用卡片 / 抽屉详情 / 证据列表 / 结论类型图标 / 置信度提示）仍需后续讨论。

## Reason

如果系统只输出最终结论，用户无法判断：

- 信息来自哪里；
- 哪些内容是事实；
- 哪些内容只是模型推测；
- 输入不足时模型是否正在编造；
- 为什么形成某个商品定位。

如果强制每一句话都对应一条原文，又会导致：

- 界面复杂；
- 综合策略难以表达；
- 容易出现形式化或错误引用；
- 增加不必要的实现成本。

采用分级证据与结论标记，可以在可追溯性和产品可用性之间取得平衡：

- 事实必须有来源；
- 洞察需要有依据；
- 推断必须显式标记；
- 假设需要用户确认；
- 资料不足必须诚实表达。

## Impact

该决定将影响：

- PRD；
- MVP Scope；
- 四层营销 Brief 数据结构；
- 输入资料解析；
- 中间状态结构；
- 用户审核页面；
- 事实修改和依赖失效；
- 引用与来源管理；
- RAG 使用边界；
- 数据库和状态存储设计；
- Agent 或工作流节点设计；
- 质量评估指标；
- 开源仓库筛选标准；
- 测试与验收标准；
- 项目 Demo 和简历表达。

> 后续技术方案必须能够回答：系统如何保存每项重要结论的类型、依据和依赖关系？

## Decision Boundary

**本决定已经确认：**

- MVP 采用五类证据与结论标记；
- 事实必须可追溯；
- 事实与推断必须分开；
- 重要洞察需要保留主要依据；
- 资料不足时不得自动编造；
- 策略结论应能回溯到事实或洞察；
- 用户修改上游内容后，下游相关内容需要重新处理或标记失效；
- 不得伪造来源。

**本决定尚未确认：**

- 引用的具体 UI；
- 是否显示置信度数值；
- 置信度如何计算；
- 来源 ID 和数据结构；
- 是否使用 RAG；
- 是否使用向量数据库；
- 是否进行网页检索；
- 是否保存原始文档片段；
- 是否使用知识图谱；
- 用户修改后采用全部重跑还是局部重跑；
- 是否使用 LangGraph State；
- 是否使用 Checkpoint；
- 数据库存储方式；
- 外部来源的可信度评估规则。

## Notes

- 用户于 2026-07-27 对该可靠性方案明确回复「确认」，通过 Decision Gate。
- 评估时存在的另外两个方案——**方案 A「只展示最终结论」** 与 **方案 B「所有结论强制逐条原文引用」**——**未被采用**，但**未被永久禁止**，作为备选方案保留（见 Session-001「Alternatives」G / H）。本决定采用两者之间的折中：分级证据标记 + 重要结论可追溯。
- **架构 / 仓库选型约束（重要）：** 本决定的可靠性原则（事实可追溯、事实与推断分离、重要洞察保留依据、修改产生依赖影响、禁止伪造来源）已成为**后续架构设计与开源仓库选型的硬约束**——任何技术方案与基底仓库必须能够支持「为每项重要结论保存类型、依据与依赖关系，并在上游修改时使下游失效」。后续讨论工作流状态 / 数据存储 / RAG / 局部重跑时，须以此为约束条件。
- 本决定确认的是**可靠性原则与五类结论标记**，不构成对 RAG / 向量数据库 / 引用 UI / 置信度算法 / 知识图谱 / LangGraph State / Checkpoint / 全量或局部重跑机制 / 外部网页检索 / 具体数据库的确认（见 Decision Boundary）。
- 与 [DEC-006](dec-006-four-layer-structured-marketing-brief.md)（四层输出主结构）、[DEC-007](dec-007-single-review-node-and-exception-pauses.md)（审核节点 + 异常暂停）协同：五类标记贯穿四层结构，审核节点是用户对事实 / 洞察 / 假设作出修正与确认的场所，Principle 6 的依赖失效与 DEC-007 的「修改后重跑」同源。
