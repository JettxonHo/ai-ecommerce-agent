# DEC-011：确定性工作流控制流程，LLM 负责受约束的语义分析与业务判断

## Type

Architecture

## Status

Accepted

## Decision

AI Ecommerce Agent 的总体执行架构采用以下职责分工：

```
确定性工作流
负责流程控制、状态一致性与规则执行

+

受约束的 LLM 分析节点
负责语义理解、信息归纳与业务判断

+

人工审核
负责关键业务结论的最终确认
```

系统**不采用**由 LLM 自由决定完整执行路径的**完全自治模式**。

工作流阶段、暂停、恢复、状态失效、局部重跑和最终结果有效性，应由**显式规则**控制。

## Deterministic Responsibilities

以下能力原则上由**确定性程序**负责：

- 必填字段检查；
- 数据类型和格式校验；
- 文件类型与大小限制；
- 原始输入保存；
- 来源 ID 分配；
- 当前工作流阶段记录；
- 状态有效、失效和待审核标记；
- 人工审核节点控制；
- 异常暂停和恢复；
- 阶段级依赖失效；
- 局部重跑范围确定；
- 输出 Schema 校验；
- 防止失效结果进入最终 Brief；
- 用户修改记录；
- 流程耗时记录；
- 运行错误和重试状态管理。

这些流程**不能**依赖 LLM 的自由判断来保证正确性。

## LLM Responsibilities

以下能力原则上由 **LLM** 负责：

- 从非结构化资料中提取商品事实候选；
- 归纳用户需求；
- 分析购买动机和购买阻碍；
- 识别潜在目标用户；
- 形成商品定位建议；
- 判断卖点优先级；
- 提出差异化表达；
- 形成内容传播策略；
- 生成结构化营销 Brief 草稿；
- 判断文本之间是否可能存在语义冲突；
- 识别可能需要人工确认的假设。

LLM 的输出必须符合**结构化契约**，并作为：

- 候选事实；
- 候选洞察；
- 模型推断；
- 待验证假设；
- 内容草稿；

进入系统。

> **未经校验或人工确认的 LLM 输出，不得自动成为已确认业务事实。**

## Hybrid Responsibilities

部分任务采用：

```
LLM 判断
  → 结构化输出
  → 程序校验
  → 工作流处理
```

### 商品事实提取

- **LLM：** 从文字或文档中提取候选事实；定位支持该事实的资料片段。
- **程序：** 校验输出结构；验证来源 ID 是否真实存在；保存事实与来源关系；标记为待审核事实。

### 资料冲突检测

- **LLM：** 判断两段资料在语义上是否可能矛盾；解释冲突点。
- **程序：** 汇总冲突；判断是否达到暂停条件；触发异常提问；保存用户处理结果。

### 证据类型分类

- **LLM：** 建议内容属于事实、洞察、推断或假设。
- **程序：** 检查是否存在真实来源；检查该类型是否符合基本规则；防止无来源内容被标记为明确事实。

### 卖点与策略分析

- **LLM：** 提出卖点、优先级和商品定位建议。
- **程序：** 检查是否关联事实或洞察；检查输出字段是否完整；将结果标记为待用户审核。

### 风险表达检测

- **LLM：** 识别可能夸大、无法验证或存在风险的表达。
- **程序：** 根据规则决定提示、阻断或转交人工审核；**不允许** LLM 自己决定忽略风险后继续。

### Brief 生成

- **LLM：** 根据已确认或当前有效的事实、洞察和策略生成执行 Brief。
- **程序：** 确认上游阶段有效；验证四层输出 Schema；检查重要结论是否保留依据；阻止过期或失效内容进入最终结果。

## Workflow Authority Principle

系统中的决策权限分为三层：

### 程序权限

决定：

- 当前处于哪个阶段；
- 是否满足继续执行条件；
- 哪些结果已经失效；
- 从哪个阶段重新运行；
- 是否需要暂停；
- 输出是否符合结构契约。

### LLM 权限

负责：

- 提供语义分析；
- 提出业务判断建议；
- 生成结构化候选结果；
- 暴露冲突、风险和不确定性。

> **LLM 不拥有对工作流状态的最终控制权。**

### 用户权限

最终确认：

- 商品事实；
- 目标用户；
- 关键需求；
- 购买阻碍；
- 商品定位；
- 卖点优先级；
- 对外传播边界；
- 最终营销 Brief。

## Non-autonomous Principle

本项目**不采用**以下默认方式：

```
用户输入
  → LLM 自主决定调用什么
  → LLM 自主决定下一步
  → LLM 自主判断何时结束
  → 直接输出最终结果
```

原因是这种方式难以稳定保证：

- 阶段一致性；
- 证据可追溯；
- 人工审核；
- 暂停和恢复；
- 局部重跑；
- 失效处理；
- 可测试性；
- 结果复现。

## Reason

当前已经确认的产品需求（Session-001，DEC-001~010）包括：

- 四层结构化输出；
- 一个强制人工审核节点；
- 异常暂停；
- 分级证据与来源关系；
- 阶段级依赖失效；
- 局部重跑；
- 下游结果一致性。

这些需求需要显式状态和稳定规则。

如果让 LLM 自由控制完整流程，系统将难以测试和保证：

- 用户修改事实后是否正确重跑；
- 失效内容是否被禁止使用；
- 人工审核后从哪里恢复；
- 来源是否实际存在；
- 输出是否符合固定结构；
- 相同状态下是否执行一致的流程。

因此，LLM 应作为工作流中的**受约束分析能力**，而不是系统流程的唯一控制者。

## Impact

该决定将影响：

- 系统架构；
- 工作流建模；
- 状态数据结构；
- 节点和阶段划分；
- 暂停与恢复机制；
- 局部重跑；
- Agent 职责；
- Tool 和 Skill 定义；
- RAG 使用方式；
- 测试策略；
- 可观测性；
- 开源仓库筛选；
- LangGraph 等框架的适用性评估。

## Decision Boundary

**本决定已经确认：**

- 工作流控制权属于确定性程序；
- LLM 负责语义分析与业务判断；
- LLM 输出应为结构化候选结果；
- 混合任务采用 LLM 判断与程序校验组合；
- LLM 不自由控制完整执行路径；
- 用户保留关键业务结论的最终确认权。

**本决定尚未确认：**

- 是否采用 LangGraph；
- 是否采用其他工作流框架；
- 工作流具体节点数量；
- 四层输出是否一层对应一个节点；
- 是否存在独立 Agent；
- 单 Agent 或 Multi-Agent；
- 状态数据模型；
- Schema 技术；
- Checkpoint 实现；
- 数据库；
- 风险检测具体规则；
- LLM 模型与供应商；
- 开源基底仓库。
