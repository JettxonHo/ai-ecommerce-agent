# DEC-014：MVP 采用按需、混合式 RAG 与分层数据访问策略

## Type

Architecture

## Status

Accepted — Amended by DEC-061

> **Current amendment:** [DEC-061](dec-061-task-scoped-private-material-and-reversible-removal.md) 明确用户商品资料默认只属于当前 Task 的有效资料集，不静默提升为跨任务共享知识；通用运营知识层与商品任务证据保持逻辑分离。以下原文继续定义访问策略。

## Decision

AI Ecommerce Agent 的 MVP 采用按**数据类型、资料规模和查询目的**选择访问方式的混合策略。

系统**不**将所有数据统一放入向量数据库，也**不**将所有资料直接塞入 LLM 上下文。

高层数据访问策略为：

```
结构化业务数据
  → 精确字段或数据库直接读取

短篇非结构化资料
  → 直接解析、全文读取或结构化提取

长篇文档、多份资料和大量评论
  → 关键词检索 + 语义检索的混合式 RAG

运营方法与平台知识
  → 独立知识库按需检索

检索结果
  → 作为带来源的证据片段写入 Workflow State
  → 提供给受约束的 LLM 分析节点
```

## Data Access Categories

### 1. 结构化业务数据

以下数据原则上采用**精确读取**：

- 商品名称、商品品类、商品价格、商品参数、推广目标；
- 当前工作流阶段、审核状态、阶段有效性、用户修改、任务运行状态、重跑起点、已确认业务字段。

> 结构化数据**不得**为了统一技术形式而强制向量化。例如，读取商品价格时应直接读取结构化字段，而不是通过语义相似度检索价格。

### 2. 短篇非结构化资料

当用户资料较短、数量较少且能够安全放入模型上下文时，可以：

- 直接读取全文；
- 执行结构化解析；
- 提取事实候选；
- 保存来源与片段位置。

> 短资料**不要求**强制经过向量检索。短资料的长度阈值和上下文预算尚未确定。

### 3. 长文档与多文档集合

以下资料在规模较大时适合采用 RAG：

- 商品详情页资料、品牌手册、用户访谈记录、用户调研报告、大量用户评论、历史营销方案、竞品分析文档、行业报告、平台指导资料、运营案例集合。

> 系统应根据当前分析任务检索相关片段，而**不是**将全部资料无差别加入 Prompt。

### 4. 运营与平台知识

商品任务之外的通用方法知识可以形成独立知识检索层，例如：

- 商品定位方法、用户需求分析方法、营销 Brief 规范、内容策略原则、平台内容规范、合规要求、已确认的运营案例、小红书官方创作指引。

任务资料与通用知识应在逻辑上区分：

```
任务证据 —— 说明这个商品和用户资料实际包含什么
运营知识 —— 说明应使用什么方法进行分析
```

> **不得**将通用运营知识误标记为当前商品的事实证据。

## Hybrid Retrieval

对于需要检索的非结构化资料，MVP 原则上采用：

```
关键词或词法检索
+
语义检索
+
可选结果排序
```

关键词检索适合：商品型号、参数名称、精确术语、品牌名称、编号、原文短语、明确关键词、平台规则条目。

语义检索适合：不同表达描述相同需求、用户评论中的隐含诉求、用户不知道原文关键词、跨文档寻找概念相关内容、从大量评论中寻找某类使用体验。

示例：

```
"带出门不累"
"放包里没压力"
"出差携带方便"
```

这些内容可能共同支持「用户关注便携性」的洞察，即使原文没有直接出现「便携」一词。

> 关键词检索和语义检索之间的权重、召回数量和排序方式尚未确定。

## RAG Responsibilities

RAG 负责：

- 根据当前任务寻找相关资料；
- 返回真实存在的来源；
- 返回可定位的证据片段；
- 支持来源引用；
- 为 LLM 分析提供相关上下文；
- 减少长资料中的无关信息；
- 支持重要洞察的依据追踪。

检索结果应写入 Workflow State，并至少能够表达：

```
retrieval_id
query_or_task
source_id
fragment_id
content
retrieval_method
```

> 以上仅为概念字段，**不是最终数据契约**。

## RAG Non-responsibilities

RAG **不负责**：

- 控制工作流阶段；
- 判断流程是否继续；
- 管理人工审核；
- 管理暂停与恢复；
- 判断哪些阶段失效；
- 决定局部重跑位置；
- 确认商品事实；
- 替用户决定商品定位；
- 直接形成最终业务决定；
- 替代结构化数据库查询；
- 替代 Workflow State；
- 自动将检索结果视为可信事实。

RAG 返回的是**候选证据**。证据是否支持某项事实、洞察或策略，仍需要经过：

```
检索 → LLM 分析 → 程序校验 → 必要时人工审核
```

## Evidence Integration

检索结果需要与 [DEC-008](dec-008-tiered-evidence-and-traceable-conclusions.md) 的证据标记机制衔接。例如：

```
source-003-fragment-021
内容：放进通勤包里基本不占位置
        ↓
insight-004
内容：部分用户重视商品的便携性
类型：有证据洞察
source_refs:
  - source-003-fragment-021
```

系统**不得**：

- 引用未被实际检索或读取的资料；
- 伪造来源 ID；
- 伪造用户评论；
- 将模型常识包装成检索结果；
- 将运营方法文档误认为商品事实来源。

## On-demand Principle

RAG **按需触发**，不要求每个步骤都检索。是否进行检索可以由确定性工作流根据以下因素决定：

- 当前任务阶段；
- 输入资料规模；
- 资料类型；
- 是否存在长文档；
- 是否存在大量评论；
- 是否需要运营方法知识；
- 当前结论是否缺乏证据；
- 用户是否提供增强资料。

> 具体触发规则尚未确定。LLM 可以提出检索建议或生成检索查询，但**是否执行检索以及检索结果如何写入状态，应受工作流控制**。

## Vector Database Boundary

本决定确认 RAG **能力**，但**不等于**已经确认必须使用独立向量数据库。MVP 的实现方式可能包括：

- 应用内索引；
- 本地向量索引；
- 关系数据库向量扩展；
- 独立向量数据库；
- 模型供应商提供的文件检索；
- 其他混合检索服务。

具体方案需要根据以下因素后续比较：资料规模、数据隔离、混合检索支持、来源管理、更新频率、部署复杂度、成本、本地开发体验、测试能力、GitHub 基底仓库结构。

> **不得**在本次归档中自动选择某个向量数据库。

## Minimum MVP Demonstration

MVP 至少应能展示按需数据访问的差异：

1. 结构化商品数据通过字段直接读取；
2. 短商品资料通过直接解析处理；
3. 大量评论、长资料或运营知识通过检索获得相关证据；
4. 检索证据与事实、洞察或策略条目建立来源关联；
5. 用户能够识别某项重要结论的主要依据。

> 具体使用多少资料、多少评论以及评测数据集仍需后续确认。

## Reason

所有资料直接放入 Prompt 会导致：上下文过长、模型成本增加、无关信息干扰、重要来源难以关联、资料规模难以扩展。

所有数据统一进入向量数据库又会导致：精确结构化字段变成模糊搜索、工作流状态与知识资料混淆、用户修改难以精确覆盖、查询结果不稳定、系统架构过度依赖语义相似度。

按需、混合式 RAG 可以结合不同方式的优势：结构化字段保证精确性；全文读取适合短资料；关键词检索适合精确术语；语义检索适合用户评论和概念表达；RAG 为重要洞察提供真实证据；Workflow State 继续承担任务状态与当前事实管理。

## Impact

该决定将影响：系统架构、数据架构、RAG Pipeline、来源与片段结构、Workflow State、商品资料解析、用户评论处理、运营知识库、小红书知识适配、LLM 上下文构建、测试与评估、开源仓库筛选、向量数据库评估、检索质量指标、项目 Demo 和简历表达。

> 后续技术方案必须回答：它是否能够根据数据类型在精确读取、全文处理、关键词检索和语义检索之间合理选择，并将检索结果以真实来源证据写入结构化状态？

## Decision Boundary

**本决定已经确认：**

- MVP 采用按需、混合式 RAG；
- 结构化数据直接读取；
- 短资料直接解析或全文使用；
- 长文档、多文档和大量评论使用检索；
- 检索结合关键词与语义能力；
- 运营知识可以使用独立知识库；
- RAG 只负责检索和证据提供；
- RAG 不负责流程控制和最终业务决策；
- 检索证据需要保留来源关系；
- RAG 与 Workflow State 分工明确。

**本决定尚未确认：**

- 具体向量数据库；
- 具体 Embedding 模型；
- BM25 或关键词检索实现；
- Reranker；
- Chunking 策略；
- Top-K；
- 混合检索权重；
- 是否使用 GraphRAG；
- 是否使用供应商文件检索；
- 是否联网搜索；
- 知识库更新方式；
- 短资料和长资料的阈值；
- RAG 触发规则；
- 最终数据契约；
- 具体 GitHub 基底仓库。
